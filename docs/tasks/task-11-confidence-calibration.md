# task-11: 신뢰도 보정 + After 측정

- 브랜치: `feat/confidence-calibration`
- 커밋 타입: `feat:`
- 선행 조건: task-10 머지 (Before 수치가 main에 있어야 한다)

## 배경

카테고리 신뢰도가 항상 `HIGH`로 나와 재분류 분기가 죽어 있다. 원인 가설은 **Category 노드가 Vision 요약 텍스트만 보고 신뢰도를 매긴다**는 구조에 있다. Vision 노드는 사진이 흐릿하든 아니든 확신에 찬 요약 문장을 만들고("소니 미러리스 카메라 본체, 외관 사용감 있음"), Category 노드에는 그 문장만 전달되므로 불확실성이 소실된다. 흐릿한 신발 사진이 "여성용 블랙 원피스"로 둔갑하고도 HIGH가 나온 것이 그 증거다.

## 설계 결정 (이 방향으로 고정)

- **Vision 노드가 식별 가능 여부를 별도 필드로 낸다.** 요약 문장과 분리된 구조화 필드여야 한다 — 문장 안에 녹이면 지금과 같은 문제가 반복된다
  - 최소 필드: 물건을 특정할 수 있는지(예: `identifiable: bool`), 그렇게 판단한 근거 한 문장
  - 사진 품질(흐림·조명·잘림)과 물건 특정 가능성을 Vision이 판단한다. Category가 재판단하지 않는다
- **Category 노드는 Vision의 판단을 신뢰도에 반영한다.** 식별 불가로 표시된 입력에서는 `HIGH`가 나올 수 없어야 한다 — 프롬프트 지시가 아니라 **코드로 상한을 건다**
- **State에 필드를 추가하되 노드 수와 분기는 그대로 둔다.** 재시도 분기는 여전히 `category` 하나뿐이다
- **API 계약은 변경하지 않는다.** `confidence`의 값 종류(HIGH/MEDIUM/LOW)와 응답 구조는 그대로다. Spring(task-08) 쪽 변경도 없다

## 작업 단계

1. Vision 구조화 출력 스키마에 식별 가능 여부 필드 추가, `DraftState`에 반영
2. Category 노드에서 식별 불가 입력의 신뢰도 상한을 코드로 강제 (LLM이 HIGH를 반환해도 낮춘다)
3. 기존 pytest 3경로(정상/재시도 성공/재시도 실패)가 계속 통과하는지 확인하고, 식별 불가 → 신뢰도 강등 경로 테스트를 추가한다 (목 LLM)
4. 확장 골든셋(task-10) 재실행 → `docs/measurements/ai-quality-baseline.md`에 **After** 절 추가, Before 대비 비교표 작성
5. 재분류 분기가 실제로 트리거되는지 확인 — 트리거 횟수를 결과 json이나 로그로 확인하고 문서에 적는다

## 하지 말 것

- 골든셋 케이스·기대값 수정 금지 (task-10에서 확정된 것을 그대로 쓴다)
- 재시도 분기 추가 금지 — `category` 하나만 유지
- API 계약 변경 금지 (`confidence` 값 종류, 응답 필드)
- 개선이 안 나왔을 때 수치를 좋게 보이게 지표 정의를 바꾸는 것 금지 — 안 나왔으면 안 나온 대로 기록하고 원인 가설을 적는다
