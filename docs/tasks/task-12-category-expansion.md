# task-12: 카테고리 확장 + 재측정 (보류)

- 브랜치: `feat/category-expansion`
- 커밋 타입: `feat:`
- 선행 조건: task-11 머지 (After가 main에 있어야 한다 — 이번 작업의 Before다)

## 배경

카테고리가 5종(`DIGITAL, FURNITURE, CLOTHING, BOOK, KITCHEN_UTENSIL`)뿐이라 그 밖의 물건이 갈 곳이 없다. task-11 측정에서 드러난 구체적 증상:

- `outside-enum-bicycle`: 선명하게 찍힌, 팔 수 있는 물건이고 Vision도 식별 가능으로 판정했다. 그런데 5종 중 고를 게 없어 Category가 LOW를 내고 재분류 후에도 LOW → **사용자가 받는 건 초안이 아니라 422 오류다.**
- `outside-enum-guitar`: DIGITAL로 분류되고 가격이 150만원(기대 5만~80만)으로 크게 벗어났다. 엉뚱한 카테고리가 가격 추정까지 오염시켰다.

task-11에서 "이건 카테고리 부족이 근본 원인이므로 카테고리를 늘린 뒤 자연 해소되는지 먼저 본다"고 미뤄둔 항목이다.

## 설계 결정 (이 방향으로 고정)

### 추가할 카테고리 — 3종 (5 → 8)

| 값 | 근거 |
|---|---|
| `SPORTS` | 자전거·운동기구·라켓. `outside-enum-bicycle`이 422로 끝난 **측정된 실패**에 대응 |
| `HOBBY` | 악기·게임기·수집품. `outside-enum-guitar`의 오분류 + 가격 이탈에 대응 |
| `APPLIANCE` | 세탁기·청소기·TV·전자레인지. 지금은 갈 곳이 아예 없는 **구조적 공백**이고, 1차 기준선에서 전기밥솥을 "블랜더"로 오식별한 것도 이 경계와 무관하지 않다 |

**개수를 8로 묶는 이유**: 실제 중고 서비스는 15종 안팎을 쓰지만, 근거 없이 늘리면 분류 난이도만 올라가고 각 카테고리를 검증할 골든셋 케이스도 없다. 유아동·뷰티·반려동물은 거래량이 큰 축이지만 **이번 측정에서 실패로 드러난 적이 없으므로 넣지 않는다.** 추가는 같은 규칙(측정된 실패 또는 명백한 구조적 공백)을 따라 그때그때 한다.

### `ETC`(기타)는 넣지 않는다

가장 쉬운 해법처럼 보이지만 넣지 않는다. 모델이 애매한 입력을 전부 `ETC`로 흘려보내는 도피처가 되고, 그러면 **task-11에서 코드로 만들어낸 저신뢰 신호가 무의미해진다** — "모르겠다"가 낮은 신뢰도가 아니라 유효한 카테고리로 세탁된다. 분류가 안 되는 입력은 낮은 신뢰도로 드러나는 편이 낫다.

### 새로 생기는 경계는 규칙으로 못 박는다

카테고리를 추가하면 **기존 카테고리와의 경계가 새로 생긴다.** 축구화는 CLOTHING인가 SPORTS인가, 전기밥솥은 KITCHEN_UTENSIL인가 APPLIANCE인가. 규칙을 정하지 않으면 실행마다 흔들린다. 아래를 Category 노드 프롬프트와 골든셋에 **동일하게** 반영한다.

| 경계 | 규칙 |
|---|---|
| CLOTHING ↔ SPORTS | 몸에 **착용하는** 옷·신발은 CLOTHING (운동화·축구화 포함). SPORTS는 **장비·기구**(자전거, 덤벨, 라켓, 텐트) |
| KITCHEN_UTENSIL ↔ APPLIANCE | 전원 없이 쓰는 조리 도구·용기는 KITCHEN_UTENSIL (팬, 냄비, 그릇). **전원을 쓰는 가전**은 APPLIANCE (밥솥, 전자레인지, 세탁기, 청소기) |
| DIGITAL ↔ APPLIANCE | 컴퓨터·모바일·카메라 등 IT 기기는 DIGITAL. 생활가전은 APPLIANCE |
| DIGITAL ↔ HOBBY | 게임기·악기는 HOBBY. 범용 IT 기기는 DIGITAL |
| BOOK ↔ HOBBY | 읽는 책은 BOOK. 음반·피규어·수집품은 HOBBY |

### API 계약은 값 목록만 늘어난다

응답 구조와 필드는 그대로다. `confidence` 값 종류도 그대로다. 백엔드 `ProductCategory`와 ai-service `Category`는 **항상 같은 값 집합**이어야 한다.

## 골든셋을 손대야 한다 — 무엇을 왜 바꾸는지 먼저 적는다

지금까지는 "골든셋 기대값 수정 금지"가 원칙이었다. 이번엔 카테고리 집합 자체가 바뀌므로 **일부 기대값이 낡은 것이 된다.** 다만 바꾸는 이유가 점수가 아니라 정의 변경이어야 하고, 무엇을 바꿨는지 전부 문서에 남긴다.

| 케이스 | 변경 | 이유 |
|---|---|---|
| `outside-enum-bicycle` | `expectedCategory` null → `SPORTS`<br>`expectedConfidence` NOT_HIGH → HIGH<br>`kind` outside_enum → normal | NOT_HIGH를 기대한 이유가 "고를 카테고리가 없어서"였다. 원인이 사라지면 기대도 바뀐다 |
| `outside-enum-guitar` | null → `HOBBY`, NOT_HIGH → HIGH, kind → normal | 위와 같다 |
| `kitchen-rice-cooker` | `KITCHEN_UTENSIL` → `APPLIANCE` | 새 경계 규칙(전원 사용 = APPLIANCE)의 직접 결과. boundaryNote도 갱신 |

**그 외 케이스의 기대값은 건드리지 않는다.** 특히 `clothing-running-shoes`·`clothing-soccer-shoes`는 SPORTS가 생겨도 CLOTHING을 유지한다(착용 규칙). 이게 지켜지는지가 이번 측정의 관전 포인트 중 하나다.

### 카테고리 밖 케이스를 최소 1건 새로 넣는다

위 변경으로 `expectedCategory: null`인 물건 케이스가 사라지면, "정답을 정의할 수 없는 입력"을 다루는 경로가 데이터로 검증되지 않는다. 8종 밖에 확실히 있는 물건 **1~2건**을 새로 추가한다(예: 유아용 카시트, 반려동물 용품). 저신뢰가 나오는지, 아니면 억지로 8종 중 하나를 골라 HIGH를 내는지 보는 케이스다.

## 작업 단계

1. 백엔드 `ProductCategory`에 3종 추가 → **DB 마이그레이션 불필요함을 확인**(`@Enumerated(STRING)`, `length=20`, 새 값 최대 9자). 값을 분기하는 코드가 없는지도 확인
2. ai-service `Category`에 동일 3종 추가, Category 노드 프롬프트에 경계 규칙 반영
3. **enum 동기화 테스트 추가** (아래 참조)
4. 골든셋 기대값 갱신 + 카테고리 밖 케이스 추가
5. 재측정 → `docs/measurements/ai-quality-baseline.md`에 "4차" 절 추가
6. task-11이 남긴 질문에 답한다: **자전거·기타가 422 대신 정상 초안으로 나오는가**

## enum 동기화 테스트

두 언어에 같은 값 집합을 손으로 유지하면 언젠가 어긋난다. **ai-service 쪽 테스트가 백엔드 `ProductCategory.java`를 읽어 `Category`와 대조**하게 한다.

방향이 그쪽인 이유: 백엔드가 원본이고 ai-service가 따라가는 관계이기 때문이다(`ai-service/CLAUDE.md`). 모노레포이므로 상대 경로로 파일에 닿을 수 있고, ai-service CI는 저장소 전체를 체크아웃한다.

- 백엔드 파일을 찾지 못하면 **스킵이 아니라 실패**로 처리한다. 조용히 넘어가면 테스트가 있으나 마나다
- 파싱은 enum 상수 목록만 추출하면 된다. Java를 제대로 파싱하려 들지 말 것

대안으로 공유 스키마 파일(JSON/YAML)에서 양쪽을 생성하는 방법이 있으나, 빌드 단계가 늘어나는 데 비해 지금 얻는 게 적다. 채택하지 않은 이유를 PR에 적는다.

## 측정 해석 주의

- **카테고리 정확도는 Before와 직접 비교할 수 없다.** 분모가 13 → 16으로 늘고, 선택지가 5 → 8로 늘어 과제 자체가 어려워졌다. 수치가 조금 떨어져도 그 자체로 실패가 아니다. 비교표에 분모 변화를 명시한다
- 신뢰도·형식·키워드 지표는 비교 가능하다
- 실행 간 변동이 크다는 것은 이미 확인됐다(같은 사진 추정가가 5만/45만/15만). ±1건 차이를 개선으로 읽지 않는다

## 하지 말 것

- `ETC` 같은 포괄 카테고리 추가 금지 (위 근거)
- 위 3건 외의 골든셋 기대값 수정 금지. 특히 운동화·축구화를 SPORTS로 바꿔서 점수를 맞추지 말 것
- 카테고리를 8종 이상으로 늘리지 말 것 — 근거 없는 확장은 이번 범위가 아니다
- 노드·분기 추가 금지, API 응답 구조 변경 금지
- 수치가 나빠졌을 때 지표 정의나 기대 범위를 손대는 것 금지. 안 나왔으면 원인 가설과 함께 그대로 기록한다
